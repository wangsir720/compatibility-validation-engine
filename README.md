# 信创适配性验证引擎（Compatibility Validation Engine）

> 输入芯片型号与业务场景，输出兼容性验证矩阵、性能与显存口径、调优参数建议、排查 FAQ
> 与方案文档草稿。
>
> **数据为公开信息与典型值，非真实交付项目，不含任何厂商私有测试数据。**

零第三方依赖，`git clone` 后直接跑。

---

## 1. 为什么做这个

国产处理器在客户现场落地时，最常见的失败不是「算力不够」，而是**「跑不起来」或「跑得不对」**：

- 芯片规格与软件栈支持范围在公开资料里对不上，客户按一份资料选型、按另一份部署，现场才发现不支持；
- 显存够不够、上下文一长会不会爆这些问题，靠经验拍脑袋，出问题才返工；
- 不同内核对应不同软件栈分支，版本漂移导致「昨天还好好的今天装不上」。

这个工具做的事是：**把「这个模型在这张卡上到底行不行」从现场踩坑变成交付前可复核的判定**。

它的核心不是算得快，是**每条结论都能点回来源**，以及**来源对不上时明确说「不下结论」**。

## 2. 覆盖哪些问题

| 能力 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| 目录与冲突检测 | 芯片/软件栈/模型 CSV | 型号目录 + 冲突清单 | 同一字段多来源不一致时显式报冲突，不静默取中间值 |
| 兼容性矩阵 | 芯片型号 + 场景 | 四档判定 + 证据链 | 每条判定必须引用到 `data/` 的具体行与来源编号 |
| 显存口径估算 | 模型 + 上下文长度 | 需求 GiB 与口径说明 | KV Cache 算不出时标「下界」，不用层数硬凑 |
| 调优建议 | 矩阵判定 | 参数建议 + 依据 + 风险 | 只对 supported / needs_tuning 给建议 |
| 排查 FAQ | 矩阵判定 | 结构化 FAQ | 每条可追溯到触发它的具体判定 |
| 方案装配 | 以上全部 | Markdown + CSV + JSON | 同样输入必须产出同样文档（已写成测试） |

**四档判定口径**（`data/assumptions.md` A-03）：

| 判定 | 触发条件 |
|---|---|
| `supported` 支持 | 显存余量 ≥ 15%，且软件栈有覆盖 |
| `needs_tuning` 需调优 | 显存够但余量 < 15% |
| `not_recommended` 不推荐 | 权重 + KV Cache 估算已超单卡显存 |
| `unknown` 待人工核实 | 关键字段缺失，或存在未解决的来源冲突 |

`unknown` 是这个项目最重要的一个档位：**不下结论，永远比错结论有用。**

## 3. 数据源与可信度分级

每条数据行都带 `source_id`（对应 `data/sources.md`）与 `credibility` 两列。

| 等级 | 含义 | 在判定中的作用 |
|---|---|---|
| `official` | 厂商官方文档 | 可直接作为依据 |
| `secondary` | 百科、聚合站、行业媒体、技术博客 | 可作为依据，结论中必须显示来源 |
| `unverified` | 单一孤证，或与官方口径矛盾 | **不参与自动判定**，仅列为待核实项 |

> 本项目**没有任何 `official` 级数据** —— 芯片规格与软件栈版本未在厂商官网公开文档中提供
> 可直接引用的规格表。这意味着引擎输出的每条判定都是**基于公开二手资料的方法论验证，
> 不是厂商认证结论**。这一点在 README 与每份输出文档中都会声明。

已自动检出并处置的来源冲突（`python -m src.cli --conflicts` 可复现）：

| 型号 | 字段 | 取值 A | 取值 B | 处置 |
|---|---|---|---|---|
| Z100 | FP32 算力 | 10.8 TFLOPS (S5) | 21.0 TFLOPS (S6, unverified) | 采用 10.8，冲突记录待核实 |
| Z100 | TDP | 250 W (S5) | 280 W (S6, unverified) | 采用 250，冲突记录待核实 |
| 7480 | 基础频率 | 2.0 GHz (S2) | 2.2 GHz (S3) | 同等级冲突 → 该字段降级为未查到，排除出判定 |
| 3490 | 最高睿频 | 3.3 GHz (S2) | 3.5 GHz (S1) | 同等级冲突 → 同上 |

**明确不含**：真实客户名称、合同金额、账号凭据、内部报价、客户业务数据、厂商私有测试数据。

## 4. 方法

```
data/chips/*.csv  ┐
data/models/*.csv ├─> catalog.py ──> 目录 + 来源冲突检测
data/sources.md   ┘                      │
data/scenarios/*.json ───────────────────┤
                                         ├─> compat_matrix.py ──> 矩阵 + 证据链
                                         │        │
                                         │        ├─> tuning_faq.build_tuning ─> 调优建议
                                         │        └─> tuning_faq.build_faq ─────> 排查 FAQ
                                         │
                                         └─> doc_assembler.render ───────────> 方案草稿
```

价目表与数据表全部外置为 CSV，`code` 里不写死任何参数值 ——
改数据不用改代码，且任何一行都能顺着 `source_id` 追回原始页面。

## 5. 快速开始

环境：Python 3.10+（验证于 3.12.8 / Windows）。**无需安装任何运行时依赖。**

```bash
# 列出可用场景
python -m src.cli --list

# 打印数据集中的全部来源冲突（推荐先跑这个）
python -m src.cli --conflicts

# 生成单个场景的方案包
python -m src.cli --scenario gov_lmm_inference

# 一次生成全部场景
python -m src.cli --all

# 跑测试
pip install pytest
python -m pytest -q
```

输出落在 `output/<场景编号>/`：

| 文件 | 内容 |
|---|---|
| `compatibility_report.md` | 方案草稿（5 章，含证据链、边界声明、免责声明） |
| `compat_matrix.csv` | 判定矩阵，可直接贴进方案 |
| `faq.csv` | 排查 FAQ，含触发来源 |
| `result.json` | 全量结构化结果 |

| DCU 型号 | 单卡显存 | 显存需求 | 余量 | 判定 | 需锁版本 |
| BW100    | 64 GiB   | 18.40 GiB | 71.2% | 支持 | 是 |
| K100-AI  | 64 GiB   | 18.40 GiB | 71.2% | 支持 | 是 |
| K100     | 32 GiB   | 18.40 GiB | 42.5% | 支持 | 是 |
| Z100     | 32 GiB   | 18.40 GiB | 42.5% | 支持 | 是 |
| Z100L    | 32 GiB   | 18.40 GiB | 42.5% | 支持 | 是 |

显存需求口径：权重 16.00 GiB × 运行时余量系数 1.15

`not_recommended` 且**不生成任何调优建议** —— 不可推荐的组合调参无效，
给建议反而是误导。

## 7. 已知局限

| # | 局限 | 影响 | 补齐方式 |
|---|---|---|---|
| 1 | **无真机验证** | 全部结论基于公开资料与估算模型 | 真实环境实测后回填 `data/` |
| 2 | **KV Cache 常算不出** | 显存需求是下界，长上下文场景会低估 | 在场景 JSON 补 `model_structure`（layers / kv_heads / head_dim） |
| 3 | **无 `official` 级数据** | 所有判定基于二手资料 | 向厂商索取规格书或查官方文档 |
| 4 | 吞吐与延迟未建模 | 只判「装不装得下」，不判「跑得快不快」 | 需实测吞吐基线（A-02 已登记为占位值） |
| 5 | 不做集群规模规划 | 仅覆盖单卡与轻量微调可行性 | 大规模训练需单独评估 |
| 6 | 数据有时效 | 版本与规格可能已变化 | `data/` 中的抓取日期即数据边界，落地前须重新核对 |

第 1、2 条是本项目最大的短板，明确写在这里而不是藏起来：
**这个工具验证的是「判定方法与证据链是否站得住」，不是「某个型号性能如何」。**
前者可以现在做，后者必须等真机。
